## 4. Как считаются показатели (сверено с TrueStats)

- **Реализация, продажи, комиссия, эквайринг, себестоимость, СПП, хранение, приёмка, штрафы, выкуп** по WB за 20.09–19.10 совпали с TrueStats один в один. По Ozon сверен один артикул (реализация, комиссия, эквайринг, логистика совпали).
- WB: комиссия = retailPriceWithDisc × кол-во − forPay − acquiringFee.
- Ozon: комиссия = −sale_commission; продажи = sale_price + coinvestment.
- **Валовая прибыль** = Реализация − (себестоимость + комиссия + эквайринг + логистика + хранение + приёмка + штрафы + прочее + реклама) + компенсации.
- **Прибыль без опер. расходов** = Валовая − налог; **Чистая прибыль** = прибыль без опер. расходов − операционные расходы (opex из Операций). Маржинальность = чистая ÷ реализация; ROI = чистая ÷ себестоимость.
- Операционные расходы распределяются поровну по дням месяца начисления (и по N месяцам, если задано распределение) — `opex_daily`.
- **Налог**, режим в Настройках (meta `tax_mode`):
  - «По факту» (по умолчанию) — реально уплаченный Налог ИП из Операций (статьи со строкой ОПиУ «Налоги»), по дням месяца начисления; только для неотфильтрованного вида, при отборе по артикулу/площадке — по ставкам.
  - «По ставкам» — УСН 6% от базы минус НДС; НДС 5/105.
  - Оба режима сразу не включаются — налог задвоится.
- **Себестоимость**: поиск по SKU / схеме (FBO/FBS) / дате действия с запасным поиском по артикулу (класс CostLookup на Python). Себестоимость 0 = нет данных (счётчик no_cost_qty). Загрузка из Excel; стартовые 200 строк из costs_seed.json.
- Маржа, ROI, оборачиваемость, GMROI. Остатки — ближайший доступный снимок.
- ОПиУ: строки по ставкам (УСН/НДС) или «Налог ИП (факт)», Чистая прибыль, «Дивиденды / вывод собственникам», «Остаётся в бизнесе». Неактивные налоговые строки скрыты.
- **Сводный отчёт**: строки — день / календарная неделя (пн–вс) / месяц; операции группируются по дате (`KEY_SQL`). У WB два недельных отчёта (Россия и СНГ/ЕАЭС) — их строки попадают в одну неделю и **складываются в одну строку**; reportId не хранится (разделить Россия/СНГ можно, но нужна полная перезагрузка финансов WB — пользователю предложено, ответа нет). Без фильтра площадки в строку входит и Ozon. Свежие дни WB — из ежедневных данных, потом заменяются недельным отчётом. Заказы — по дате заказа. При фильтре площадки/артикулов налог всегда по ставкам.
- **Схема FBO/FBS**: колонка `scheme` в orders/fin/stocks; при фильтре схемы не учитываются opex и `orders_hist` (не делятся по схемам); реклама/хранение WB — на FBO. Дашборд: таблица «Wildberries: FBO и FBS» за период.
- Карточки дашборда сгруппированы (`KPI_GROUPS` в app.js): Прибыль; Заказы, продажи, выплаты; Расходы маркетплейса; Себестоимость, налоги, расходы бизнеса; Остатки.
- Блок «Сегодня» (today.py): сегодня vs вчера к этому времени, по часам, топ артикулов; WB разбит на FBO/FBS; учитывает фильтр площадки и схемы; карточка «WB FBS — не отправлено» (таблица `fbs_tasks`: новые / на сборке / собраны и ждут приёмки WB, возраст самого старого, красная > 24 ч).
- Месячный отчёт (monthly.py): полные недели пн–вс, у которых четверг в месяце; готов через 3 дня после конца месяца.
- ДДС: по счетам, разделы операционная / финансовая / инвестиционная.
- Операции: ручной ввод, повтор на N месяцев, кнопка «Загрузить из Google Таблицы», метка «таблица» у импортированных.

## 5. Склады → Ozon и план поставок Ozon

Данные есть по каждому кластеру: и спрос, и остатки. Кнопка «Обновить склады Ozon» (режим `--ozon-wh`); ночью обновляется вместе со всем остальным.

По каждой паре артикул × кластер:
- **Заказов в день** = заказы без отмен с этим кластером доставки (cluster_to) за N дней (7/14/30, по умолчанию **14**) / N.
- **Остаток** = свободный остаток на складах кластера; **В пути** = обещанное поступление (promised).
- **Дней запаса** = остаток / заказов в день. Цвета: < 14 дней — красный, < 30 — жёлтый.
- **Везти** = max(0, заказов в день × целевой запас (по умолчанию **30** дней) − остаток − в пути).
- **Нелокальных заказов, %** = доля заказов кластера, отгруженных с другого кластера (cluster_from ≠ cluster_to).
- Считается по каждому кластеру отдельно: излишек в одном кластере не закрывает дефицит в другом.
- Пример (в справке): Екатеринбург 42 заказа за 14 дней = 3/день, остаток 20, в пути 10, запас 30 → везти 90 − 20 − 10 = 60; Москва 10/день, остаток 500 → 0.
- Итоги по кластеру: заказы, остаток, в пути, дни запаса, % нелокальных, артикулов в дефиците (запас < 14 дней), всего везти.
- **Excel «План поставок»**: лист «Сводка», лист «Все кластеры», по листу на каждый кластер; количество округляется вверх, цветовая заливка по запасу.
- Договорённость: везём во все кластеры; кратность коробки и минимальная партия не нужны (Ozon сам ограничивает лимитами по кластерам). Шаблон загрузки поставки в Ozon пользователь пришлёт позже.

## 6. Склады → Wildberries и план поставок WB (`app/wbplan.py`)

**Что известно:** спрос по федеральным округам — точно (поле региона в каждом заказе). Остатки — **только общей цифрой по стране**: WB скрыл склады и в остатках, и в заказах (поле склада отгрузки в заказах = «Склад WB РФ», проверено на данных за 40 дней). Регионального отчёта об остатках в ЛК WB тоже нет. Сервис Postavleno пользователь использовать не будет.

**Что НЕ делаем:** не парсим витрину WB программой (card.wb.ru / u-card с dest, как Postavleno) и не меняем адрес на сайте WB скриптом — витрина закрыта антиботом, автоматизация сайта от имени аккаунта сотрудника = обход защиты. Решение принято и объяснено пользователю.

**Расчёт по артикулу** (параметры: спрос за 7/14/30 дней, запас в днях — вверху страницы):
1. Спрос округа P_d = заказы без отмен из округа ÷ дней; держать = P_d × запас.
2. Оценка остатка: общий остаток S раскладывается по округам пропорционально P_d **только среди округов, где товар есть**; округ с отметкой «нет на месте» → 0. Непроверенный округ считается «есть».
3. Потребность округа = max(0, держать − оценка), округление вверх. Излишек одного округа не уменьшает поставку в другой.
4. Округ → склад отгрузки (meta `wb_wh_map`, редактируется на странице; пустое = не везём, но спрос округа всё равно расходует общий остаток). По умолчанию: Центральный → Коледино, Северо-Западный → Санкт-Петербург (Шушары), Южный → Краснодар, Северо-Кавказский → Невинномысск, Приволжский → Казань, Уральский → Екатеринбург, Сибирский → Новосибирск, Дальневосточный → Хабаровск, Другие страны → не везём.
5. Мелкие партии: если на склад по артикулу < `wb_min_qty` (по умолчанию 5), переносим на самый крупный склад артикула.
- Без проверок план = (общий спрос × запас − S), разложенный по доле спроса.
- Пример (в справке): 20 шт./день, S = 600, запас 45. Без проверок: Центр 45% → 135, Приволжье 60, Юг 45, Урал 30, Сибирь 30 = 300. Урал «нет»: оценка Урала 0, 600 делится на 18 шт./день → Центр 105, Приволжье 47, Юг 35, **Урал 90**, Сибирь 24 = 301.

**Проверка наличия по срокам доставки** (ручная, но быстрая):
- WB показывает дату доставки прямо на карточках на странице бренда (подтвердил пользователь). Долгая доставка = товара в округе нет. Проверять каждый товар отдельно пользователь отказался (400 проверок) — поэтому одна страница бренда на округ.
- Закладка-букмарклет **«WB → дашборд»** (константа `WB_BOOKMARKLET` в app.js): на открытой человеком странице бренда находит карточки (`[data-nm-id]` или ссылки `/catalog/{nm}/detail`), в каждой ищет по текстовым узлам «сегодня / завтра / послезавтра / D месяца», копирует JSON `{src:'wb-delivery', at, addr, url, items:[[nm, label]]}` в буфер и пишет, сколько карточек нашла и какой округ угадан по адресу. После изменения кода закладку нужно перетащить заново.
- В дашборде «Вставить данные с WB» → POST `/api/wh/wb_presence` {district, data}; округ подставляется по адресу (`CITY_DISTRICT`). Чужие nm пропускаются. Таблица `wb_presence(nm, district, days, label, checked_at, addr)`; DELETE `/api/wh/wb_presence?district=` очищает округ.
- Маршрут (`CHECK_CITY`): Москва, Санкт-Петербург, Краснодар, Невинномысск, Казань, Екатеринбург, Новосибирск, Хабаровск. Сотрудник один раз сохраняет в профиле WB по пункту выдачи в каждом городе и переключает адрес в два клика. На странице статус по округу: «нужно проверить» / «✓ сегодня» / «пора обновить» (> 7 дней).
- Порог «нет на месте» — доставка ≥ `wb_presence_threshold` дней (по умолчанию 4; из Тулы пользователь видел +3 дня при наличии). Отметки действуют 14 дней (`FRESH_DAYS`).
- Настройки — POST `/api/wh/wb_settings` {map, threshold, min_qty}.
- **Не проверено на реальном WB:** букмарклет протестирован только на макете страницы. Если на живом сайте не найдёт карточек или округ — поправить селекторы/регулярку.

**Страница:** KPI; таблица «Округа и склады отгрузки» (доля, в день, склад, наличие, потребность); «План по складам»; блок проверки с маршрутом, порогом и мин. партией; матрица «артикул × округ» (виды: Везти, Доставка дн., Оценка остатка, Заказов в день, Доля спроса; красный — нет на месте, зелёный — есть).
**Excel** `/api/wh/wb_plan`: «Сводка» по складам, «Все склады», лист на каждый склад (артикул, название, nm, баркод, везти, спрос округов склада, общий остаток, «Нет на месте»).

## 7. Контроль цен (`app/prices.py`)

**Цель (от пользователя):** цена для покупателя на сайте не должна опускаться ниже **МРЦ** — минимальной розничной цены из прайс-листа MOCHEQI Professional (D:\MP\2025 ВБ_Прайс-лист MOCHEQI Professional.pdf, последняя колонка «МРЦ»; «Базовая цена» — оптовая). МРЦ — нижний порог, ниже продавать нельзя. Только свои карточки; сайт не парсим. В коде таблица называется `rrp` (историческое имя), в интерфейсе — «МРЦ».

**Данные (исходная версия; актуальный расчёт — ниже, «Обновление 03–05.11»):**
- Цена для покупателя: WB — `orders.paid` последнего заказа (finishedPrice, уже со СПП); Ozon — `cur_prices.buyer_price` (marketing_price из `/v5/product/info/prices`), иначе последний заказ. Заказы за 7 дней; ts у Ozon с пробелом → нормализуем `REPLACE(ts,' ','T')`, сортировка строго по ts (была ошибка с ORDER BY по номеру колонки).
- Ваша цена (до СПП): WB — `discounts-prices-api /api/v2/list/goods/filter` (нужна категория токена «Цены и скидки»; при 401/403 meta `wb_prices_access=0`, берём `orders.price`); Ozon — marketing_seller_price/price.
- СПП (WB) = (ваша цена − цена покупателя) ÷ ваша цена.
- Таблицы: `rrp(mp DEFAULT 'all', article, price, updated_at)` — одна МРЦ на обе площадки; `cur_prices(mp, article, mp_sku, seller_price, buyer_price, base_price, discount, ts)`.

**Статусы:** отклонение = (цена покупателя − МРЦ) ÷ МРЦ. «ниже МРЦ» если < −`price_tolerance` (по умолчанию 0%); «близко к МРЦ» если < `price_warn` (5%); иначе «в норме»; ещё «нет заказов» и «МРЦ не задана». Причина для «ниже»: ваша цена < МРЦ → «ваша цена ниже МРЦ»; WB → «СПП WB»; Ozon → «акции Ozon». Окно минимальной цены `price_hours` (24). Нужная ваша цена при СПП = МРЦ ÷ (1 − СПП).

**Страница:** фильтр Все/WB/Ozon, «только с МРЦ», «Проверить сейчас» (`mode=prices`), «Загрузить МРЦ» (текст «артикул цена» или xlsx со столбцами Артикул + МРЦ/РРЦ/Цена; галочка «заменить все»), «Экспорт CSV»; клик по ячейке МРЦ — правка (пусто = удалить). Артикул — ссылка на карточку (`wildberries.ru/catalog/{nm}/detail.aspx`, `ozon.ru/product/{sku}/`). Карандаш ✎ — копирует артикул (WB — nm) в буфер и открывает кабинет: WB `seller.wildberries.ru/discount-and-prices`, Ozon `seller.ozon.ru/app/products/{product_id}/edit` (product_id после первой проверки цен), иначе список товаров. **Адреса кабинетов не проверены** — шаблоны в `SHOP_URL`/`CABINET_URL` в app.js. API: GET `/api/prices`, POST `/api/prices/rrp` {rows|text|file, replace}, POST `/api/prices/settings` {tolerance, warn, hours}; meta отдаёт `price_alerts`. Права: страница `prices` (галочка «Контроль цен» у сотрудника).

## 8. Пользователи и доступ

## Что убрать для продукта (на 07.11.2026, mp-control)

**Сначала — чтобы не задеть Mocheqi на том же ПК** (сейчас D:\MPControl стоит рядом с D:\MP\dashboard):
- `install_schedule.bat` / `remove_schedule.bat` регистрируют и удаляют задачи Windows с теми же именами, что у Mocheqi («MP Dashboard - daily update / price check / today orders», `-Force`) — **не запускать из D:\MPControl**, пока имена не изменены, иначе ночные загрузки Mocheqi будут перезаписаны или удалены.
- `widget_autostart.bat` создаёт тот же ярлык «Mocheqi widget.lnk» в автозагрузке; `allow_network.bat` — то же правило брандмауэра «MP Dashboard 8765».
- Порт **8765** занят Mocheqi: при пробном запуске MP Control рядом задать другой порт в `config.ini` (`[server] port`).

**Название и данные Mocheqi в коде:**
- Название: `index.html` (title, логотип «M»), `app.js` (вход, заголовок, текст «Данные для входа», подсказка «страница бренда MOCHEQI»), `appconfig.py` и `config.example.ini` (имя магазина по умолчанию), `widget.pyw`, `widget*.bat`.
- `db.py`: стартовые магазины «Mocheqi» / «Mocheqi_Ozon».
- `app/rrp_seed.json` + `prices.py`: МРЦ из прайса MOCHEQI автоматически грузятся в пустую таблицу — у нового селлера их быть не должно.
- `gsheet.py`: жёстко заданы лист «Мосийчук М.В. 2026», колонки счетов (СБЕР, наличные Игорь/Наташа/Олег, Касса), правила типов операций и год 2026 — нужна настраиваемая схема импорта.
- `server/` (install.sh, update.sh, after_upload.sh, README, инструкции): пользователь и папки `mocheqi`, `/opt/mocheqi`, служба `mocheqi.service`.
- `help_build/` и `help.html`: заголовки и примеры с Mocheqi; `README.md`.
- Бэклог продукта (из раздела 10): установка для других селлеров на отдельном сервере, затем SaaS — мультиарендность, PostgreSQL, очередь задач, оплата, 152-ФЗ.
